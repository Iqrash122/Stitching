9. HISTORICAL MEASUREMENT SAFETY
==================================================

Measurements must be independent snapshots, not live links to mutable template values.

Each snapshot stores:
- Order line and piece index.
- Template identity and copied name/version.
- Revision and current-revision marker.
- Capture/freeze timestamps.
- Source snapshot and superseded revision.
- Reason for confirmed-order corrections.

Each snapshot value copies:
- Field code and label.
- Section and sequence.
- Type and unit.
- Required and validation settings.
- Choice options.
- Typed value and explicit is_set state.

Zero must be distinguishable from an unset measurement.

Shared mode:
One snapshot applies to the line quantity.

Per-piece mode:
Exactly one current complete snapshot for each piece numbered 1..quantity.

“Use same measurements for every piece” must deep-copy values.

“Load previous measurements” must:
- Restrict to the same customer and compatible garment/template.
- Use frozen measurements from confirmed, non-cancelled orders.
- Prefer the latest delivered order.
- Preview source order, date, revision and units.
- Copy values independently.
- Require deliberate review for incompatible fields or units.

Never silently reinterpret inches as centimeters.

Example:
An old order with Chest = 42 must remain 42 after a new copied order is edited to 44.

Template edits, option changes and archive actions must not alter historical printouts.

Changing customer, product, quantity or measurement mode after draft measurements exist requires an explicit reset/reconciliation flow.

After confirmation:
- Freeze the original measurements.
- Allow active-order corrections only as new reasoned revisions.
- Retain previous revisions.
- Disallow modifications after delivery or cancellation.

10. FINANCIAL CALCULATIONS
==================================================

Implement a single authoritative backend calculation engine.

For each line:
Gross = quantity × unit price.
Apply line percentage or fixed discount.
A fixed line discount applies to the entire line, not every piece.

Apply header discount after line discounts.

Allocate header discount proportionally across lines using deterministic largest-remainder allocation in currency minor units.

Allocated shares must sum exactly to the header discount.

Validate:
- Percentages between 0 and 100.
- No negative prices or discounts.
- Fixed discounts cannot exceed the relevant base.
- Fully discounted orders are valid and require no payment.

Examples:
2 × 1500 = 3000; 10% discount → 2700.
5000 − 500 fixed discount → 4500.
5000 − 200 fixed discount → 4800.
3000 − 200 + 700 = 3500; 10% header discount → 3150.

Implement documented tax behavior for:
- Tax-excluded pricing.
- Tax-included pricing.
- Multiple taxes.
- Fixed taxes.
- Ordered/grouped taxes where configured.

Snapshot tax definitions and calculated amounts.

Document the exact discount/tax calculation order and rounding policy.

Frontend previews must match backend results. Never trust submitted totals.

Optional direct-cost reporting:
- Distinguish unknown cost from known zero.
- Exclude tax from revenue/margin.
- Show cost coverage.
- Return N/A where a reliable margin cannot be calculated.
- Do not call stitching margin “whole-business net profit.”
- Do not erase incurred costs when revenue is credited/refunded.

11. COMPLETE BILLING INTEGRATION
==================================================

Laravel does not provide the previous Odoo accounting implementation. Build a coherent billing subledger explicitly.

Provide:
- Draft invoices.
- Posted invoices.
- Advances.
- Multiple partial payments.
- Payment allocations.
- Credit notes.
- Refunds.
- Reversals.
- Outstanding balances.
- Printable invoices and receipts.
- Customer billing history.

Invoice rules:
- One active primary invoice per order.
- Transaction-safe unique numbering.
- Duplicate requests cannot create duplicate invoices.
- Invoice customer, currency, source lines, quantities,
  discounts, taxes and totals must match the confirmed order.
- Posted financial records are immutable.
- Corrections use credits/reversals and linked correction orders.
- Never silently rewrite or delete posted transactions.

Payment rules:
- Store amount, date, method, reference and settlement state.
- Separate a payment from its invoice allocations.
- Sum allocation amounts, not the full payment once per invoice.
- Unallocated money must not falsely mark an order as paid.
- Ordinary partial payments leave the remaining receivable open.
- Do not silently write off differences.

Example:
Invoice 2200.
Payment 1000 → due 1200.
Payment 500 → due 700.
Payment 700 → due 0.
Preserve all three receipts and their allocations.

Concurrency:
- Use transactions and row locks.
- Bind idempotency keys to request payloads.
- Repeating the same request returns its existing result.
- Reusing a key with a different payload is rejected.
- Reject stale balances with a clear refresh message.
- Prevent double-click and simultaneous-tab overpayment.

Credits and refunds:
- Credit against original invoice quantities, prices and taxes.
- Cumulative credits cannot exceed the original eligible amount/quantity.
- Apply credit against unpaid receivables before calculating refundable credit.
- Refund only a valid remaining refundable amount.
- Preserve credit allocations, refund records and reversal history.
- Prevent duplicate refunds.

Show separately:
- Invoiced amount.
- Allocated cash/payment amount.
- Credit/noncash settlement.
- Remaining receivable.
- Unapplied customer credit.
- Refund obligation.
- Payment settlement state.

Do not present settlement by credit as cash collected.

Support cash and manually recorded bank payments. Distinguish pending bank settlement from settled funds.

Do not pretend to charge a bank/card or integrate a gateway without an actual authorized provider integration.

Cancellation:
Cancelling production does not erase the invoice, payment or debt.
Show a billing exception requiring a deliberate credit/refund decision.

Store effective financial dates and recorded timestamps.
Historical reports must reconstruct the requested cutoff rather than use today's residual balances.
